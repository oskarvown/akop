# Stage 0 — Анализ репозитория и контракт данных (ревизия 4)

Иерархия источников истины (при конфликте — сверху вниз): (1) подтверждённые Александром бизнес-решения и уточнения Stage 0; (2) актуальные документы Stage 0 (`docs/*`); (3) Roadmap «Дебиторка-бот» v1.3 — для требований, не уточнённых Stage 0.

Синхронизировано с актуальным содержимым `docs/IMPLEMENTATION_PLAN.md`, `docs/DATA_CONTRACT.md`, `docs/ASSUMPTIONS.md`, `docs/REQUIREMENTS_TRACEABILITY.md`. Ниже — только выжимка решений; при любом расхождении между этим файлом и `docs/*` приоритет имеют файлы в `docs/`.

## 1. Модель входных файлов

Один файл = один отдел (не менеджер). Четыре отдела: СЗФО 1, СЗФО 2, Региональный, Москва. Внутри файла — несколько `ManagerGroup` (в подтверждённых файлах отдела «Региональный» — 8 групп: 7 физических лиц и 1 организационная группа/филиал), число динамическое и не входит в fingerprint.

```text
AuditCycle
└── report_date
    ├── SourceFile: СЗФО 1        → несколько ManagerGroup
    ├── SourceFile: СЗФО 2        → несколько ManagerGroup
    ├── SourceFile: Региональный  → несколько ManagerGroup   (подтверждено файлами)
    └── SourceFile: Москва        → несколько ManagerGroup
```

Жизненный цикл: `collecting` = 0–4 уникальных отдела (0/1/2/3 — нормальные промежуточные состояния); `completed` = ровно 4 валидных отдела одной даты, все прошли валидацию.

`SourceFile.department_id` — обязательное поле. Способ определения отдела — открытый вопрос (`docs/ASSUMPTIONS.md` §1.1): внутренний маркер / подтверждённое правило именования / выбор пользователем при загрузке / ручное подтверждение.

`ManagerGroup` стабилен между аудитами через канонический ключ `department_id + normalized_name` — `manager_group_id` переиспользуется, не создаётся заново на каждый цикл (`docs/DATA_CONTRACT.md` §2.3).

## 2. Правила комплектности аудита (Stage 3)

- один активный файл на отдел, два одновременно активных файла одного отдела недопустимы;
- точный дубликат по SHA-256 отклоняется;
- новый файл уже загруженного отдела требует явного подтверждения замены;
- все 4 файла — одна отчётная дата, иначе ошибка блокирует финализацию;
- каждый файл проходит структурную валидацию независимо;
- отсутствие отдела блокирует автозавершение и сравнение недель;
- изменение числа `ManagerGroup` — не ошибка;
- бот показывает полученные/недостающие отделы.

Автофинализация: `4 уникальных отдела AND совпадающие даты AND все файлы валидны AND истёк idle timeout`. Неполный комплект после timeout не переходит в `completed`.

Полный список из 22 обязательных тестовых сценариев — в `docs/REQUIREMENTS_TRACEABILITY.md` (20 сценариев ревизии 2 + стабильность `ManagerGroup` между аудитами (ревизия 3) + сохранение иерархии уровней 2–4 без двойного суммирования (ревизия 4)).

## 4. Data contract отдела «Региональный» (подтверждён)

- 17 физических колонок (индексы 0–16 / A–Q), лист `TDSheet`, формат `.xls` (BIFF8). Классификация: `A` — иерархическая колонка; `B–E` — служебные/пустые; `F` — «Отсрочка платежа» (не денежная, неаддитивная, тип `int | null`); `G–P` — 10 денежных колонок; `Q` — комментарий.
- `analytical header`: строки Excel 6–7; `hierarchy header block`: строки 6–10.
- `outline_level`: 0 = `ManagerGroup`, 1 = контрагент, 2 = договор, 3 = объект расчётов/заказ, 4 = расчётный документ/УПД. Уровни 2–4 **распознаются и сохраняются** в модели с родительскими связями (`contract_id`/`object_id`/`document_id`) для детализации отчёта — не выбрасываются. Их суммы **не суммируются повторно** при построении агрегатов reconciliation (§6 DATA_CONTRACT) — это раскрытие той же суммы, что уже учтена на строке контрагента уровня 1. 3 псевдо-level1-строки шапки (`Параметры:`/пусто/`Отбор:`) исключаются позиционно.
- `regional_2026-07-08`: колонка F (индекс 5, «Отсрочка платежа») и H (индекс 7, «Сумма документа») физически скрыты (`hidden=1`); колонка G (индекс 6, «Сумма кредита») не скрыта, но шириной 42 твипа против ~4500–5100 у соседних — визуально сжата. Скрытая/сжатая колонка не считается отсутствующей.
- Отклонение файла не ограничивается только удалением/добавлением/перемещением колонки — включает также неверный лист, повреждённую книгу, нераспознаваемый заголовок, неоднозначное соответствие колонок, недопустимые типы и другие критические структурные ошибки (`docs/DATA_CONTRACT.md` §4.1).
- Колонка «Не просрочено» обязательна физически для fingerprint «Региональный»; её отсутствие в regional-файле — основание для отклонения по fingerprint, а не повод для fallback-вычисления. Fallback `not_due = total_debt − Σ buckets` применяется только к legacy/alternative шаблону или к другому подтверждённому в будущем fingerprint, явно допускающему отсутствие колонки (`docs/DATA_CONTRACT.md` §5.1).
- Reconciliation «Итого» — по метрикам, не блоком: аддитивные денежные метрики (Сумма документа, Долг, Аванс, Не просрочено, 5 корзин) сверяются построчно; «Сумма кредита» имеет отдельную политику (диагностика, не отказ); «Отсрочка платежа» и структурные/текстовые поля — неаддитивны, сумма не проверяется (`docs/DATA_CONTRACT.md` §6).
- Подтверждённое расхождение «Итого» по «Сумме кредита»: `regional_2026-07-01` = 3 000 000, `regional_2026-07-08` = 4 000 000, `regional_2026-06-24`/`regional_2026-06-11` = 0 — не ошибка парсера, диагностика.
- Отделы СЗФО 1/2 и Москва — статус TENTATIVE, fingerprint не подтверждён и не экстраполируется.

## 5. Matching и правило исчезновения контрагента

Закрытый вопрос: одноимённые контрагенты у разных `ManagerGroup` — разные компании (подтверждено Александром). Ключ идентичности: `department_id + manager_group_id + normalized_counterparty_name`; при нескольких договорах внутри пары — дополнительно `contract_id + object_id + document_id`. Кредитные лимиты одноимённых компаний разных `ManagerGroup` суммируются как независимые позиции.

Ключ сопоставления между неделями — тот же (`department_id + manager_group_id + normalized_counterparty_name`), с учётом стабильного `manager_group_id`. Подтверждённый default (не блокирует Stage 5): смена `ManagerGroup`/отдела не объединяется автоматически — исчезновение у одной пары и появление у другой. Отдельный неблокирующий вопрос на будущее — нужен ли ручной перенос истории (`docs/ASSUMPTIONS.md` §1.3). Правило «компания не должна исчезать» проверяется только по полному комплекту всех 4 отделов.

## 8. Изоляция исходных файлов

Исходные файлы хранятся в локальной директории `private_inputs/` в корне рабочей директории, которая исключена из version control правилом `/private_inputs/` в `.gitignore`. Файлы не отслеживаются Git и не должны попадать в коммиты. Все 8 идентифицированных исходных файлов (7 Excel-файлов, используемых как входы/fixtures парсера, и 1 справочный PDF, не являющийся входом парсера) физически перемещены туда (не удалены). Git-репозиторий не инициализирован. В `docs/*` и в этом plan-файле используются только алиасы, без ФИО, названий контрагентов и оригинальных имён файлов.

## Что НЕ делается на Stage 0

- Не пишется код `app/`, `tests/`, Telegram handlers, Excel-парсер.
- Не создаются синтетические «эталонные» файлы взамен реальных.
- Не создаются Alembic/SQLAlchemy артефакты (это Stage 1). Docker не используется (см. `docs/ASSUMPTIONS.md` §2.3).
- Stage 1 не запускается до подтверждения ревизии 4 пользователем.
