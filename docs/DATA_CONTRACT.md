## 2. Логическая модель файла и цикла

```text
AuditCycle
└── report_date
    ├── SourceFile: СЗФО 1        (department_id = szfo_1)
    │   └── несколько ManagerGroup
    ├── SourceFile: СЗФО 2        (department_id = szfo_2)
    │   └── несколько ManagerGroup
    ├── SourceFile: Региональный  (department_id = regional)  ← подтверждено
    │   └── несколько ManagerGroup
    ├── SourceFile: Москва        (department_id = moscow)
    │   └── несколько ManagerGroup
    └── SourceFile: Фокин         (department_id = fokin)     ← добавлен 30.07.2026, §2.4
        └── одна ManagerGroup (один менеджер)
```

- `SourceFile.department` — обязательное поле, enum `{szfo_1, szfo_2, regional, moscow, fokin}`; после валидации файла Александр выбирает отдел явной Telegram-кнопкой (решение Stage 3, часть 1).
- `AuditCycle.report_date` уникален; дата берётся из содержимого файла. Файл другой даты относится к отдельному циклу, а при уже открытом `collecting`-цикле требует явного подтверждения создания второго.
- `SourceFile.audit_cycle_id` — nullable FK на `audit_cycles.id`: `NULL` допустим только для legacy-строк Stage 2; новые Telegram-загрузки Stage 3 всегда сохраняются внутри цикла.
- `SourceFile.lifecycle_status` — PostgreSQL enum `active/superseded`. Заменённый файл не удаляется: его SHA-256 остаётся в глобальном уникальном ограничении и истории.
- Частичный уникальный индекс `uq_source_file_active_per_department (audit_cycle_id, department) WHERE lifecycle_status = 'active'` гарантирует один активный файл отдела на цикл.

### 2.1. Жизненный цикл AuditCycle по числу отделов

```text
AuditCycle.status = collecting:  0–4 уникальных отдела с активным файлом каждый (0, 1, 2, 3 или 4 — нормальные промежуточные состояния)
AuditCycle.status = completed:   ровно 5 валидных отделов, все SourceFile прошли структурную валидацию, одна общая report_date
AuditCycle.status = expired:     неполный collecting после AUDIT_MAX_REMINDERS успешных напоминаний + AUDIT_EXPIRE_GRACE_SECONDS без активности (Stage 3.2); никогда не означает completed
```

Поля Stage 3.2 на `audit_cycles`: `notification_chat_id` (фиксируется при создании из `AUDIT_NOTIFICATION_CHAT_ID`), `reminder_count`, `last_reminder_at`, `reminder_claim_token` / `reminder_claimed_at` (lease на отправку), `expired_at`.

Утверждение «один аудит = ровно 5 файлов» относится только к состоянию `completed`. Во время сбора (`collecting`) число активных файлов может быть от 0 до 4; добавление пятого уникального отдела атомарно переводит цикл в `completed`. Неполный комплект никогда не становится `completed`. Изменения разрешены только при `status == collecting`; `completed` и `expired` неизменяемы.

### 2.2. ManagerGroup вместо «Manager»

В подтверждённых файлах отдела «Региональный» строки уровня `outline_level = 0` — это **8 групп**: 7 физических лиц и 1 организационная группа/филиал. Поэтому сущность называется `ManagerGroup`, хотя в интерфейсе бота может оставаться слово «менеджер».

Правила:

- `ManagerGroup.raw_name` — непрозрачная строка, взятая как есть из ячейки; **не валидируется** по шаблону ФИО (иначе отфильтруется организационная группа);
- количество `ManagerGroup` внутри файла — динамическое, **не входит** в template fingerprint и не является критерием валидности файла или комплектности аудита;
- реальные значения `raw_name` из production-файлов не переносятся в коммитируемые документы/fixtures (см. `docs/ASSUMPTIONS.md` §3).

### 2.3. Стабильная идентичность ManagerGroup между аудитами

`manager_group_id` не может быть новым на каждый `AuditCycle` — иначе одна и та же группа в двух неделях ошибочно станет двумя разными сущностями и сравнение недель (Stage 5) будет некорректным.

```text
ManagerGroup.raw_name             — исходное значение ячейки, как есть
ManagerGroup.normalized_name      — нормализованное значение (NFKC, trim, регистр, схлопывание пробелов)
Канонический ключ ManagerGroup    = department_id + normalized_name
manager_group_id                  — постоянный ID, разрешаемый через канонический ключ;
                                     при повторном появлении того же (department_id, normalized_name)
                                     переиспользуется существующий manager_group_id, новый не создаётся.
```

Это то же правило нормализации, что и для контрагентов (§7), применённое к `ManagerGroup`.

## 3. Единый template fingerprint всех 5 отделов (подтверждён)

Подтверждён на 4 файлах отдела «Региональный» (`regional_2026-06-11`, `regional_2026-06-24`, `regional_2026-07-01`, `regional_2026-07-08`). По бизнес-решению Александра (см. статус выше и §10) это единый входной контракт для **всех пяти отделов** — СЗФО 1, СЗФО 2, Региональный, Москва, Фокин. Файл любого из пяти отделов с иной физической структурой (иное число/позиции колонок, иной заголовок) отклоняется валидатором с диагностикой (§4.1) и рассматривается как отдельное изменение контракта, требующее отдельного пересмотра этого документа, — а не как повод считать структуру данного отдела в принципе неизвестной.

- Формат: `.xls` (BIFF8), лист `TDSheet`.
- Физическое число колонок: **17** (индексы 0–16, Excel-буквы A–Q).
- Заголовок — многострочный, с объединёнными/пустыми ячейками. При нумерации строк Excel с единицы:
  - `analytical header`: строки 6–7 — названия аналитических (не только финансовых) колонок: иерархическая колонка A (Менеджер/Партнёр), служебные колонки B–E, «Отсрочка платежа» (F, не денежная), 10 денежных колонок (G–P), безымянная колонка комментария (Q) — точный состав см. §3.1;
  - `hierarchy header block`: строки 6–10 — надписи для вложенных уровней иерархии (Партнёр → Договор → Объект расчётов → Расчётный документ/УПД), частично перекрывается с analytical header по строкам 6–7.
- Строки 1–5 (Excel-нумерация) — блок параметров отчёта: дата отчёта (`Дата отчета: DD.MM.YYYY`), название графика, строка отбора менеджерских групп. **Дату отчёта парсить из этого блока, не из даты загрузки файла.**
- `outline_level` по строкам и их роль в модели данных:
  - `0` — строка `ManagerGroup`;
  - `1` — строка контрагента (партнёра); на этом уровне читаются агрегированные финансовые показатели контрагента, используемые в reconciliation (§6);
  - `2` — строка договора (`contract_id`);
  - `3` — строка заказа/объекта расчётов (`object_id`);
  - `4` — строка расчётного документа/УПД (`document_id`).
  - Уровни 2–4 **распознаются и сохраняются в модели** с явными родительскими связями (`contract_id`/`object_id`/`document_id`, привязанными к контрагенту уровня 1 и к `ManagerGroup` уровня 0) — они нужны для детализации отчёта (§9: `… → договор → документ`) и для ключей идентичности финансовых позиций (§7: `contract_id + object_id + document_id`). Они **не выбрасываются** из модели.
  - При этом уровни 2–4 **исключаются из reconciliation агрегатов** (§6): их суммы — это раскрытие (детализация) той же самой суммы, что уже учтена на строке контрагента уровня 1, а не дополнительные величины. Повторное суммирование строк 1 и 2–4 в рамках одной и той же метрики недопустимо (двойной счёт). Reconciliation с «Итого» выполняется только по строкам уровня 1.
  - **Важный нюанс парсера**: в блоке параметров (строки 1–3 Excel) движок чтения также присваивает `outline_level = 1` трём строкам шапки (`Параметры:`, пустая строка, `Отбор:`). Эти строки должны быть исключены позиционно (до первой строки `ManagerGroup`), а не просчитаны как контрагенты.

## 4. Скрытые и визуально сжатые колонки — правило независимости парсинга

Подтверждено на `regional_2026-07-08.xls`:

- колонка `F` (индекс 5, «Отсрочка платежа») — физически скрыта (`hidden=1`);
- колонка `H` (индекс 7, «Сумма документа») — физически скрыта (`hidden=1`);
- колонка `G` (индекс 6, «Сумма кредита») — **не** скрыта (`hidden=0`), но экстремально узкая (ширина 42 твипа против ~4500–5100 у соседних колонок) — визуально «сжата» до незаметности в Excel.

**Правило:** валидатор и парсер должны читать значения ячеек по физической позиции колонки независимо от свойства `hidden` и от ширины колонки. Скрытая или визуально сжатая колонка **не считается отсутствующей** и не должна приводить к отклонению файла или к диагностике «колонка не найдена».

**Пустой хвост колонок/строк:** Excel (особенно `.xlsx` через openpyxl) может сообщать `max_column > 17` или `max_row` больше реальных данных, если справа от Q задана ширина пустых столбцов или внизу листа есть пустые строки. Парсер обрезает такой хвост до последней колонки/строки с непустым содержимым; после обрезки fingerprint по-прежнему требует **ровно 17** колонок (A–Q) и строку «Итого» последней. Колонка **с данными** правее Q или непустые строки после «Итого» не обрезаются и приводят к отклонению файла (§4.1).

### 4.1. Основания для отклонения файла (не ограничивается позицией колонок)

Файл отклоняется, если выполняется любое из условий (список открытый, не исчерпывающий):

- обязательная колонка реально удалена, добавлена или перемещена относительно позиции, зафиксированной в fingerprint (кейс `invalid_2026-07-15_missing_columns`, см. §8);
- неверный/отсутствующий лист (например, нет листа `TDSheet` или структура листа не соответствует ожидаемой);
- повреждённая или нечитаемая книга (ошибка чтения формата `.xls`/`.xlsx`);
- несовместимый или нераспознаваемый заголовок (analytical/hierarchy header не сопоставляется с fingerprint);
- неоднозначное соответствие колонок fingerprint (например, из-за сдвига после ошибки чтения объединённых ячеек не удаётся однозначно определить позицию обязательной колонки);
- недопустимые типы данных в обязательных числовых колонках (нечисловое значение там, где ожидается `Decimal`);
- отсутствие строки «Итого» или её структурная повреждённость;
- другие критические структурные ошибки, не позволяющие достоверно сопоставить строки файла с моделью данных.

Скрытая/сжатая колонка в этот список не входит и не является основанием для отклонения.

## 5. Формулы (детерминированные, без изменений относительно Roadmap)

- `Общая просрочка = overdue_1_7 + overdue_8_14 + overdue_15_21 + overdue_22_30 + overdue_over_31`.
- `Изменение долга = current.total_debt − previous.total_debt`.
- `Чистое снижение долга = max(previous.total_debt − current.total_debt, 0)`.
- `Чистый рост долга = max(current.total_debt − previous.total_debt, 0)`.
- Правило года для даты без года в комментарии: подставить год отчётной даты; если дата уже прошла относительно отчётной даты — взять следующий год.
- Денежные значения — только `Decimal`, округление до копеек, пустая ячейка ≠ 0 на этапе валидации (различать «нет данных» и «ноль»).

### 5.1. Fallback для «Не просрочено» — ограниченная область применения

```text
not_due = total_debt − sum(overdue_1_7, overdue_8_14, overdue_15_21, overdue_22_30, overdue_over_31)
```

Для единого подтверждённого fingerprint (§3, действует для всех 5 отделов) колонка «Не просрочено» **обязательна физически** (см. §3.1, индекс 10). Если в файле любого из 5 отделов эта колонка физически отсутствует — файл **отклоняется по несоответствию fingerprint** (§4.1), а не «спасается» fallback-вычислением. Fallback не должен превращать структурно невалидный файл в валидный.

Fallback-формула применяется только в одном из двух случаев:

1. для отдельно поддерживаемого legacy/alternative template (например, `legacy_parser_fixture.xls`), собственный контракт которого явно допускает отсутствие колонки «Не просрочено»;
2. после подтверждения отдельного альтернативного fingerprint (например, для будущего изменения шаблона у одного из отделов), который явно допускает отсутствие этой колонки — только тогда, когда такой fingerprint зафиксирован в этом документе.

Условия применения fallback (когда он разрешён контрактом соответствующего шаблона): присутствуют все пять корзин просрочки, результат ≥ 0, сходится применимая для этого шаблона сверка «Итого».

## 6. Reconciliation строки «Итого» — по метрикам, не блоком

Отменено универсальное правило «все 17 колонок Итого должны совпадать с суммой строк контрагентов». Метрики разделены на три группы:

```text
Аддитивные денежные метрики (сумма строк контрагентов должна совпадать с «Итого», с допуском на округление):
- Сумма документа
- Долг
- Аванс
- Не просрочено
- 5 корзин просрочки (1–7, 8–14, 15–21, 22–30, свыше 31)

Метрика с отдельной политикой (не блокирует файл при расхождении):
- Сумма кредита — см. §6.2

Неаддитивные / структурные поля (сумма не имеет смысла, «Итого» не проверяется):
- Отсрочка платежа
- названия и иерархические поля (Менеджер/Партнёр/Договор/Объект расчётов/Расчётный документ)
- комментарий менеджера
```

### 6.1. Отсрочка платежа — не аддитивная метрика

«Отсрочка платежа» — это срок (дней), атрибут договорных условий конкретного контрагента, а не денежная величина, которую можно складывать по строкам и сверять с «Итого».

Единый контракт поля:

```text
payment_deferral_days: int | null
```

При чтении Excel ячейка физически может быть числовой (в т.ч. с плавающей точкой при некорректном форматировании исходной книги). После валидации значение должно приводиться к целому числу дней. Дробное, отрицательное или нечисловое значение — **ошибка данных соответствующей записи** (не файла целиком). Пустая ячейка — допустимое значение `null`.

Для этого поля проверяется **допустимость значения на уровне отдельной записи**, но **не сумма** по колонке и не сверка с «Итого».

### 6.2. Расхождение «Итого» по «Сумме кредита» — подтверждённый кейс, не ошибка

Александр подтвердил бизнес-правило: одноимённые контрагенты у разных `ManagerGroup` — независимые сущности (см. §7). Кредитный лимит учитывается отдельно для каждой пары `отдел + ManagerGroup + контрагент`; одинаковые лимиты у одноимённых компаний разных менеджерских групп **суммируются как независимые позиции**, а не дедуплицируются. Из-за иной логики агрегации в исходной книге 1С сумма независимых позиций «Сумма кредита» может не совпадать со значением «Итого» самого файла:

- проверено: `regional_2026-07-01` — сумма по строкам минус «Итого» = **3 000 000** (сумма по строкам больше);
- проверено: `regional_2026-07-08` — расхождение = **4 000 000** (сумма по строкам больше);
- проверено: `regional_2026-06-24` и `regional_2026-06-11` — расхождение = 0.

Правило обработки:

1. файл **не отклоняется** из-за этого расхождения;
2. сохраняется исходное значение «Итого» файла (как есть, для аудита);
3. сохраняется рассчитанное ботом значение (сумма независимых позиций по правилу §7);
4. расхождение регистрируется как диагностическая запись (info/warning), не как ошибка;
5. основным расчётным значением бота считается сумма независимых позиций, а не «Итого» исходной книги.

Все остальные аддитивные денежные метрики (§6, первая группа) при расхождении с «Итого» **остаются блокирующей ошибкой** до подтверждения «принять с предупреждением» или замены файла (Roadmap §3.3) — исключение действует только для «Суммы кредита».

## 7. Идентичность контрагента и matching (подтверждённое бизнес-правило)

Александр подтвердил: **одинаково названные контрагенты у разных `ManagerGroup` — разные компании.** Вопрос закрыт (см. `docs/ASSUMPTIONS.md` §2.1).

Запрещено:

- глобально дедуплицировать контрагентов только по названию;
- объединять финансовые показатели одноимённых контрагентов разных `ManagerGroup`;
- автоматически связывать такие записи через fuzzy matching.

**Ключ идентичности контрагента внутри аудита:**

```text
department_id + manager_group_id + normalized_counterparty_name
```

Если внутри одной пары `отдел + ManagerGroup` одно и то же название представлено несколькими договорами/заказами — это одна сущность контрагента, а отдельные финансовые позиции различаются дополнительными ключами:

```text
contract_id + object_id + document_id
```

`raw_name` (оригинальное название) хранится отдельно от `normalized_name` во всех сущностях.

**Ключ сопоставления между неделями** (Stage 5):

```text
department_id + manager_group_id + normalized_counterparty_name
```

`manager_group_id` в этом ключе — стабильный ID, разрешаемый через канонический ключ `department_id + normalized_manager_group_name` (§2.3), а не новый ID на каждый `AuditCycle`.

- Fuzzy matching допускается только для формирования кандидатов (диагностика/ручное подтверждение Александром), никогда — для автоматического объединения финансовых записей.
- **Подтверждённый default (не блокирует Stage 5):** если одноимённая компания «переходит» к другому `ManagerGroup` или в другой отдел — у прежней пары `отдел+группа` она считается исчезнувшей, у новой — впервые появившейся; автоматическое объединение истории не выполняется. Эта логика реализуется в базовой версии Stage 5 без дополнительных решений.
- **Отдельный неблокирующий вопрос на будущее** (см. `docs/ASSUMPTIONS.md` §1.3): нужен ли в дальнейшем механизм **ручного** подтверждённого переноса истории контрагента при доказанном переходе к другому `ManagerGroup`/отделу (аналог alias, но между парами «отдел+группа»). Отсутствие ответа на этот вопрос не блокирует базовую реализацию Stage 5.
- Правило «компания не должна исчезать» проверяется только после получения **полного комплекта из всех 5 отделов** за отчётную дату. До этого делать вывод об исчезновении компании нельзя — неполный комплект интерпретируется как ошибка/незавершённость данных, а не как результат сравнения.

## 8. Негативный fixture: `invalid_2026-07-15_missing_columns.xlsx`

Файл физически содержит **12 колонок** вместо обязательных 17. Отсутствуют колонки: «Отсрочка платежа», «Сумма кредита», «Сумма документа», «Не просрочено», корзина «От 15 до 21 дня». Основная причина отклонения — несоответствие числа и позиций обязательных колонок эталонному fingerprint (§4.1). Расхождение агрегатов (сумма строк контрагентов не совпадает с «Итого» файла) фиксируется как дополнительная диагностика, не как основная причина отказа.

## 9. Уровни агрегации отчёта (Stage 4)

```text
Общий итог
→ отдел
→ ManagerGroup
→ контрагент
→ договор
→ документ
```

Глубина по договорам/документам и число `ManagerGroup` могут отличаться между файлами и не влияют на валидность.

Уровни `договор`/`документ` в отчёте — это детализация (раскрытие) той же суммы контрагента, а не дополнительное слагаемое: агрегаты «отдел»/«ManagerGroup»/«контрагент» строятся по строкам уровня 1 (§3), вложенные строки уровня 2–4 при построении этих агрегатов повторно не суммируются.

## 10. Отделы СЗФО 1 / СЗФО 2 / Москва / Фокин — единый шаблон подтверждён бизнес-решением

**Подтверждено Александром 28.07.2026 (бизнес-решение):** СЗФО 1, СЗФО 2, Региональный и Москва передают файлы строго по одному и тому же утверждённому шаблону из 17 физических колонок (§3, §3.1). Это решение снимает статус TENTATIVE для структуры файла: подтверждённый fingerprint — единый входной контракт для этих отделов, а не только для «Регионального».

**Дополнено 30.07.2026:** утверждённый состав отделов расширен до пяти — добавлен отдел **«Фокин»** (§2.4). Он использует тот же единый шаблон без исключений; отдельного бизнес-решения по формату для него не требовалось, так как контракт §3 распространяется на любой отдел, добавляемый в канонический список `Department`.

Практические следствия:

- валидатор и парсер (`app/infrastructure/excel/`) применяются к файлу любого из 5 отделов без изменений — они не зависят от `Department` и проверяют только физическую структуру;
- отдельный fingerprint или отдельный модуль парсера на каждый отдел **не создаётся** — это было бы неоправданным дублированием при отсутствии фактических структурных различий;
- реальные файлы СЗФО 1, СЗФО 2, Москвы и Фокина по-прежнему физически не получены — это не блокирует Stage 2 (парсер/валидатор считается реализованным и применимым ко всем 5 отделам), но остаётся отдельной необходимостью для Stage 3/5 (нужны реальные данные всех 5 отделов для полного недельного комплекта и сравнения недель);
- если при получении реального файла СЗФО 1, СЗФО 2, Москвы или Фокина обнаружится физическое расхождение со шаблоном (иное число/позиции колонок, иной заголовок) — это отдельное изменение контракта: файл будет отклонён валидатором с диагностикой (§4.1), а данный документ и fingerprint потребуется пересмотреть для этого конкретного случая. До появления такого сигнала действует единый шаблон.
