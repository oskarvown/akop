## Модель входных файлов (актуальная, заменяет «1 файл = 1 менеджер»)

```text
AuditCycle
└── report_date
    ├── SourceFile: СЗФО 1        → несколько ManagerGroup
    ├── SourceFile: СЗФО 2        → несколько ManagerGroup
    ├── SourceFile: Региональный  → несколько ManagerGroup   (подтверждено файлами)
    ├── SourceFile: Москва        → несколько ManagerGroup
    └── SourceFile: Фокин         → одна ManagerGroup (один менеджер, добавлен 30.07.2026)
```

Все 5 отделов используют единый 17-колоночный fingerprint (подтверждено бизнес-решением Александра, см. `docs/DATA_CONTRACT.md` §3, §10) — парсер и валидатор идентичны для всех отделов, различается только значение `department`.

Число `ManagerGroup` внутри файла динамическое и не входит в критерии валидности/комплектности (для «Фокина» это число равно 1 — тоже допустимое значение, не частный случай). Подробности типов, формул, fingerprint — в `docs/DATA_CONTRACT.md`. Открытые вопросы — в `docs/ASSUMPTIONS.md`.

### Жизненный цикл AuditCycle по числу отделов

```text
collecting AuditCycle: 0–4 уникальных отдела с активным файлом каждый (промежуточные состояния 0/1/2/3/4 — нормальны)
completed AuditCycle:  ровно 5 валидных отделов, одна общая report_date, все SourceFile прошли структурную валидацию
```

## Правила комплектности аудита (Stage 3, заменяют «до 30 файлов» / «10+10+10»)

- один активный файл на каждый из 5 отделов; два одновременно активных файла одного отдела в одном цикле не допускаются;
- точный дубликат по SHA-256 отклоняется;
- новый файл уже загруженного отдела (не дубликат) требует явного подтверждения замены;
- файлы группируются в разные `AuditCycle` по `report_date`; открытие второго цикла при уже существующем `collecting` требует явного подтверждения;
- каждый файл проходит обязательную структурную валидацию независимо;
- отсутствие хотя бы одного отдела блокирует автозавершение цикла и сравнение недель;
- изменение числа `ManagerGroup` внутри отдела между неделями — не ошибка;
- бот показывает полученные и недостающие отделы после каждой загрузки.

Условие автофинализации (все обязательны одновременно):

```text
получены 5 уникальных отделов в одном AuditCycle
AND все 5 SourceFile имеют report_date этого AuditCycle
AND все 5 файлов прошли обязательную валидацию
```

В части 1 цикл атомарно становится `completed` сразу при строгом 5/5. Idle timeout, напоминания и присвоение `expired` не входят в часть 1; значение `expired` только зарезервировано в enum. Неполный комплект никогда не становится `completed`. Любой статус, отличный от `collecting`, неизменяем сервисными add/replace-операциями.

### Stage 5 (сравнение недель)

- Заблокирован до получения **двух последовательных полных комплектов**. Полный комплект = 5 файлов (по одному на каждый отдел, включая «Фокин») за одну отчётную дату. Для двух недель нужно 10 валидных файлов, покрывающих все 5 отделов на каждую из дат.
- Сейчас есть 4 разные отчётные даты только одного отдела («Региональный») — это не является полным комплектом ни для одной недели.
- Базовая логика matching и обработки смены `ManagerGroup`/отдела (исчезновение/появление без автообъединения) уже определена в `docs/DATA_CONTRACT.md` §7 и не требует дополнительных решений для начала реализации Stage 5 — блокер связан только с отсутствием тестовых данных, не с открытыми бизнес-вопросами.

- `app/bot/` — каркас aiogram 3, доработан по итогам финальной проверки безопасности:
  - `AllowlistMiddleware` зарегистрирована как **outer middleware на `dispatcher.update`** (`app/main.py`), а не на отдельных observer'ах (`message`/`callback_query`). Это единая точка авторизации для **абсолютно любого** типа Telegram-события (message, callback_query, inline_query, chat_member и т.д.); ни один будущий handler не может обойти проверку, зарегистрировавшись на другом observer'е диспетчера.
  - Мидлварь дополнительно **явно запрещает group/supergroup** даже для разрешённого `ALLOWED_USER_ID` — бот отвечает только в private chat (апдейты без привязанного чата, например `inline_query`, по типу чата не блокируются, т.к. группой не являются).
  - Health-check хендлер `/start` вынесен в фабрику `get_start_router()` (аналогично `get_root_router()`), а не module-level singleton — иначе повторная сборка `Dispatcher` в одном процессе (актуально для тестов) падала с `RuntimeError: Router is already attached...`.
  - `app/main.py` — точка входа (`python -m app.main`, long polling).
- `scripts/deploy/debitor-bot.service` — systemd unit для production (без Docker, см. `docs/ASSUMPTIONS.md` §2.3). Проверено: не содержит локальных путей macOS, использует production-пути `/opt/debitor-bot` и отдельного системного пользователя `debitor-bot`.
- `requirements.txt` / `requirements-dev.txt`, `pytest.ini`, `README.md` с инструкцией локального запуска и деплоя.
- Тесты (12 шт., все проходят):
  - `tests/unit/test_config.py` (3): валидный DSN из окружения; отклонение неположительного `AUDIT_IDLE_TIMEOUT_SECONDS`; отсутствие обязательных переменных → понятная `ConfigurationError` с перечислением недостающих имён.
  - `tests/unit/test_allowlist_middleware.py` (6): разрешённый пользователь в private chat пропускается; посторонний пользователь блокируется; разрешённый пользователь в group и в supergroup блокируется (параметризованный тест даёт 2 test id — `[group]`/`[supergroup]` — отсюда 6, а не 5 сценариев); неавторизованный `callback_query` блокируется; апдейт без чата не блокируется по типу чата.

### Семантика `SourceFileStatus.INVALID` (зафиксировано по явному запросу пользователя)

В схеме есть два значения статуса — `valid` и `invalid`. Фактически реализованный в Stage 2 вариант:

- **Невалидные файлы вообще не сохраняются в БД** — ни `SourceFile`, ни `DebtPosition`. Единственная функция сохранения (`persist_valid_source_file`) осознанно поднимает `ValueError`, если её вызвать с невалидным `ValidationResult`, вместо того чтобы создать запись со `status=invalid`.
- `SourceFileStatus.INVALID` **зарезервирован в схеме на будущее** (вероятно, Stage 3 — история/аудит отклонённых загрузок, чтобы показывать пользователю причину отказа спустя время), но в Stage 2 это значение **нигде не присваивается** — ни в одной функции `app/infrastructure/excel/persistence.py`.

## Отчёт по Stage 3, часть 1 (07.08.2026)

- Добавлены `AuditCycle` (`collecting/completed/expired`) и история файлов `SourceFileLifecycle` (`active/superseded`). `expired` зарезервирован, но не присваивается в части 1.
- `add_source_file_atomic` и `replace_source_file_atomic` полностью владеют транзакциями. Цикл блокируется через `SELECT ... FOR UPDATE`; повторное создание одной даты обрабатывается одним прозрачным retry всей add-транзакции. Замена никогда не создаёт отсутствующий цикл.
- Частичный уникальный индекс `uq_source_file_active_per_department` гарантирует один активный файл отдела в цикле; `uq_source_file_sha256` обеспечивает глобальный дедуп, включая исторические superseded-файлы.
- Предварительные read-only функции сами закрывают транзакции и возвращают immutable DTO, построенные column projection без lazy relationships. Атомарные операции получают только примитивы.
- Telegram FSM принимает `.xls/.xlsx`, валидирует файл, предлагает 5 кнопок отделов, **подтверждение выбранного отдела** (Подтвердить / Другой отдел / Отмена), подтверждение второго цикла и атомарной замены, защищает callback через `upload_token`, поддерживает `/cancel` и `/undo` (снять ошибочное ACTIVE-назначение и сразу выбрать другой отдел без повторной загрузки файла). `/status` читает состояние напрямую из PostgreSQL.
- Повторный preflight перед миграцией: `source_files=0`, найдены все 5 реальных файлов, совпадений SHA-256 с БД `0/5`. Реальные Excel-файлы в проект не копировались.
- Миграция `a3c100000001` прошла `upgrade head`, `downgrade -1`, повторный `upgrade head`, а также чистый путь `downgrade base → upgrade head` на пустой dev-БД. После `downgrade base` в PostgreSQL не остаётся Stage 3 артефактов: ни `audit_cycles`, ни enum `audit_cycle_status`/`source_file_lifecycle`, ни индекса `uq_source_file_active_per_department`, ни колонок/FK `audit_cycle_id`/`lifecycle_status`. Создать отдельную временную БД не удалось из-за отсутствия у роли PostgreSQL права `CREATEDB`; права не изменялись.
- Атомарность замены: внутри одной транзакции сначала `SUPERSEDED` (иначе partial unique index не даст вставить второй `ACTIVE`), затем insert нового файла. При любой ошибке до commit старый файл остаётся `ACTIVE`; committed-состояние никогда не содержит `SUPERSEDED` без нового `ACTIVE`.
- FSM хранится в `MemoryStorage` с `SimpleEventIsolation`: параллельные Telegram updates одного чата сериализуются, второй документ получает «ещё не завершена» вместо перезаписи FSM. После рестарта бота callback-токены становятся недействительными (пустое FSM-состояние → «кнопка устарела»).
- Зависимости обновлены до `aiogram==3.30.0` + `aiohttp==3.14.3` (устранение advisories старого aiohttp 3.10.x).
- `ManagerGroup`/`Counterparty` создаются через PostgreSQL `ON CONFLICT DO NOTHING` по identity-constraint, чтобы параллельные загрузки одного отдела не роняли валидный файл.
- `/status` режет ответ на сообщения ≤4096 символов; успешная загрузка показывает сумму долга; имена файлов/причины отказа экранируются для `ParseMode.HTML`.
