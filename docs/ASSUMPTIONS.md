## 1. Открытые вопросы (требуют решения до соответствующего этапа)

### 1.2. Безымянная колонка комментария — снято по бизнес-решению §2.0

В подтверждённом единого шаблона комментарий менеджера находится в последней (17-й, индекс 16) колонке, у которой нет заголовка ни в одной из строк шапки; это распознаётся позиционно, не по названию колонки. Ранее было открыто, будет ли эта колонка на той же позиции в файлах СЗФО 1/2/Москва/Фокин — после бизнес-решения Александра о едином шаблоне всех 5 отделов (§2.0) вопрос закрыт: позиция и отсутствие заголовка считаются частью единого контракта для всех отделов, пока реальный файл конкретного отдела не покажет иное (тогда это будет отдельное изменение контракта, см. `docs/DATA_CONTRACT.md` §10).

### 1.3. Ручной перенос истории контрагента при смене ManagerGroup/отдела (неблокирующий, на будущее)

Базовое правило Stage 5 уже определено и не требует решения для запуска: при переходе одноимённой компании к другому `ManagerGroup` или в другой отдел — у прежней пары «отдел+группа» она считается исчезнувшей, у новой — впервые появившейся; автоматическое объединение истории не выполняется (см. `docs/DATA_CONTRACT.md` §7). Этот default реализуется в базовой версии Stage 5 без дополнительных согласований.

Открытым остаётся только вопрос **будущего расширения**: нужен ли отдельный механизм ручного подтверждённого переноса истории контрагента, когда Александр точно знает, что это одна и та же компания, реально перешедшая к другому менеджеру/в другой отдел (аналог alias, но на уровне пары «отдел+группа»). Отсутствие ответа на этот вопрос **не блокирует** базовую реализацию Stage 5.

## 2. Закрытые вопросы (решены, зафиксированы, не открыты повторно)

### 2.0. Fingerprint отделов СЗФО 1 / СЗФО 2 / Москва / Фокин — ЗАКРЫТО (перенесено из §1.4)

Ранее (§1.4, до 28.07.2026) считалось полностью не подтверждённым (TENTATIVE в `docs/DATA_CONTRACT.md` §10), а письменное подтверждение Александра — недостаточным без реальных файлов каждого отдела. **Бизнес-решение Александра от 28.07.2026 закрывает этот вопрос**: все отделы передают файлы строго по единому утверждённому шаблону из 17 колонок (см. `docs/DATA_CONTRACT.md` §3, §10). Подтверждённый fingerprint действует как единый входной контракт для всех отделов; отдельный fingerprint или парсер на отдел не создаётся без фактических структурных различий.

**Дополнено 30.07.2026:** состав отделов расширен до пяти — добавлен отдел «Фокин» (`docs/DATA_CONTRACT.md` §2.4). Единый шаблон распространяется на него автоматически, отдельного подтверждения формата не потребовалось.

Реальные файлы СЗФО 1, СЗФО 2, Москвы и Фокина физически по-прежнему не получены — это остаётся отдельной потребностью для комплектности аудита (Stage 3/5), но больше не рассматривается как неподтверждённость структуры файла.

### 2.1. Одинаковое название контрагента у разных менеджерских групп — ЗАКРЫТО

Александр подтвердил: одинаково названные контрагенты у разных `ManagerGroup` считаются **разными компаниями**. Правило зафиксировано в `docs/DATA_CONTRACT.md` §7 как ключ идентичности `department_id + manager_group_id + normalized_counterparty_name`. Глобальная дедупликация по названию, объединение финансовых показателей и автоматическое fuzzy-объединение таких записей — запрещены.

### 2.2. Расхождение «Итого» по «Сумме кредита» — не ошибка парсера

Подтверждено вычислениями на реальных файлах (см. `docs/DATA_CONTRACT.md` §6.2): расхождения в 3 000 000 (`regional_2026-07-01`) и 4 000 000 (`regional_2026-07-08`) объясняются тем, что «Итого» исходной книги 1С агрегирует «Сумму кредита» по иной логике, чем сумма независимых позиций «отдел+ManagerGroup+контрагент». Бот использует собственный расчёт (сумму независимых позиций) как основное значение и сохраняет расхождение как диагностику, не как ошибку. Это единственная денежная метрика с таким исключением; для остальных аддитивных метрик расхождение с «Итого» остаётся блокирующей ошибкой.

### 2.3. Docker не используется — ЗАКРЫТО

Пользователь подтвердил: Docker **не нужен**. Roadmap §5/§8 предлагает Docker Compose, но Stage 0 **заменяет** это решением без контейнеров:

- Python-приложение в `venv` на VPS;
- PostgreSQL — системный сервис или managed DB;
- процесс бота — `systemd` unit (`scripts/deploy/debitor-bot.service`, Stage 7);
- резервное копирование — cron + `pg_dump` (Stage 7);
- Redis/Celery не добавляются.

`Dockerfile`, `docker-compose.yml` и прочие Docker-артефакты **не создаются** на Stage 1 и Stage 7.

### 2.4. Способ определения отдела файла — ЗАКРЫТО в Stage 3, часть 1

После успешной структурной валидации файла Александр явно выбирает один из пяти отделов inline-кнопкой Telegram, затем подтверждает выбор (в подтверждении показывается сумма долга файла). Имя файла и состав менеджерских групп не используются как источник истины для `Department`. Выбранное значение повторно проверяется атомарным сервисом при сохранении/замене. Ошибочное назначение в открытом (`collecting`) цикле отменяется через подтверждаемое `/undo` / кнопку «Отменить последнюю загрузку»: файл переводится в `REVOKED` (без физического удаления), слот отдела освобождается; COMPLETED/EXPIRED циклы undo не меняет. Решение реализовано в `app/bot/handlers/upload.py` и `app/application/audit_service.py`, покрыто `tests/integration/test_bot_upload_flow.py` / `test_audit_service_stage3.py`.

## 3. Обращение с исходными файлами (безопасность/приватность)

- Реальные production-файлы (полученные как вложения в диалоге) содержат коммерческие данные (суммы задолженности, названия контрагентов) и персональные данные (ФИО сотрудников отдела «Региональный»). Они **не коммитятся** в репозиторий.
- Исходные файлы хранятся в локальной директории `private_inputs/` в корне рабочей директории, которая исключена из version control правилом `/private_inputs/` в `.gitignore`. Файлы не отслеживаются Git и не должны попадать в коммиты. Репозиторий пока не является git-репозиторием (`git init` не выполнялся). Файлы физически присутствуют в `private_inputs/` (перемещены туда точным списком, ничего не удалено). Полный список файлов и их безопасные алиасы — в `docs/DATA_CONTRACT.md` §1.
- Для `tests/fixtures` (Stage 2) необходимо подготовить **анонимизированные** версии на основе подтверждённой структуры (`docs/DATA_CONTRACT.md` §3):
  - псевдонимизированные названия контрагентов и `ManagerGroup.raw_name`;
  - синтетические либо пропорционально преобразованные суммы, сохраняющие математические инварианты (совпадение/несовпадение «Итого» по каждой аддитивной метрике, знак `not_due`, наличие кейса диагностического расхождения по «Сумме кредита»); реальные production-суммы (кроме уже зафиксированных диагностических величин 3 000 000 и 4 000 000, которые являются математическими фактами расхождения, а не коммерческой суммой конкретного контрагента) в fixtures не переносятся;
  - сохранённая структура строк, `outline_level`, многострочные/объединённые заголовки, скрытые и визуально сжатые колонки (как в `regional_2026-07-08`), контрольные итоги и намеренно созданные расхождения (как в `invalid_2026-07-15_missing_columns`);
  - без скрытых листов, Excel-комментариев, внешних ссылок, изображений и прочих остаточных метаданных исходных книг;
  - имена файлов fixtures — только безопасные алиасы (`regional_2026-06-11.xls` и т.п.), без реальных ФИО и оригинальных имён файлов.
- В `docs/*` и `.cursor/plans/*` реальные ФИО, названия компаний, оригинальные имена файлов и исходные комментарии не используются — только алиасы и обезличенные описания.

## 4. Плейсхолдеры конфигурации (Stage 1, не блокирует Stage 0)

Значения ниже — плейсхолдеры для `.env.example`, реальные значения предоставляются перед деплоем (Stage 7):

- `BOT_TOKEN` — токен Telegram-бота (создаёт и хранит Александр);
- `ALLOWED_USER_IDS` — один или несколько Telegram `user_id` через запятую для allowlist (private chat only);
- `DB_*` (host/port/name/user/password) — параметры PostgreSQL;
- `AUDIT_IDLE_TIMEOUT_SECONDS` — idle до первого напоминания (production default 86400);
- `AUDIT_REMINDER_INTERVAL_SECONDS` — интервал между успешными напоминаниями (86400);
- `AUDIT_MAX_REMINDERS` — число успешных напоминаний до grace (2);
- `AUDIT_EXPIRE_GRACE_SECONDS` — пауза после последнего успешного напоминания до EXPIRED (86400);
- `AUDIT_NOTIFICATION_CHAT_ID` — единственный получатель напоминаний (Саша); пишется в `AuditCycle.notification_chat_id` при создании цикла;
- `AUDIT_SCHEDULER_POLL_SECONDS` — период опроса scheduler (60);
- `AUDIT_REMINDER_CLAIM_TTL_SECONDS` — TTL claim-lease (300);
- `AUDIT_REMINDER_SEND_TIMEOUT_SECONDS` — timeout Telegram send, строго меньше claim TTL (30);
- `AUDIT_REMINDER_ERROR_BACKOFF_SECONDS` — мин. пауза после ошибки Telegram перед повторным claim (900);
- `OPENROUTER_API_KEY`, `OPENROUTER_BASE_URL`, `OPENROUTER_MODEL`, `OPENROUTER_TIMEOUT_SECONDS`, `OPENROUTER_MAX_RETRIES` — Stage 4.4 OpenRouter для ambiguous comments (провайдер зафиксирован: OpenRouter);
- `COMMENT_ENRICHMENT_*` / `COMMENT_*_VERSION` — claim/run timeouts, attempts, batch, parser/prompt/schema/redaction versions (Stage 4.4);
- `LLM_API_KEY`, `LLM_MODEL` — legacy aliases, подставляются в OpenRouter key/model если `OPENROUTER_*` пусты.

### 4.1. Ограничения доставки напоминаний (Stage 3.2)

- Exactly-once с Telegram невозможен: между успешным `send_message` и записью `reminder_count` есть crash window → после TTL возможен редкий повтор.
- Activity сразу после pre-send recheck может привести к доставке устаревшего текста, но `record` обязан стать no-op (claim очищен). PG-транзакция во время Telegram API не удерживается.
- Ошибка Telegram не увеличивает `reminder_count` и не двигает к EXPIRED; повтор не чаще error backoff (не каждые 60 с бесконечно).
